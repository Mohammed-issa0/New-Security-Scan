# الفصل الثالث: تحليل المتطلبات

## 3.1 تحليل أصحاب المصلحة (Stakeholders)

| صاحب المصلحة | الدور | التوقعات |
|--------------|-------|----------|
| المستخدم العادي | مطوّر أو محلل أمن | إنشاء فحوصات، متابعة نتائج، تصدير تقارير |
| مدير النظام (Admin) | مسؤول المنصة | إدارة مستخدمين، طابور، باقات، سجلات تدقيق |
| خادم VPS | منفّذ الفحص | استقبال مهام، إرجاع نتائج عبر Webhook |
| Stripe | بوابة دفع | تأكيد شراء الباقات والرصيد الإضافي |
| Jira Cloud | إدارة مشاريع | استقبال تذاكر الثغرات عبر OAuth |

## 3.4 حالات الاستخدام

### UC-01: إنشاء فحص أمني جديد

**الفاعل:** مستخدم مسجّل | **الشرط المسبق:** باقة فعّالة وهدف مُعرَّف

**التدفق الرئيسي:**
1. يفتح المستخدم صفحة فحص جديد.
2. يختار الهدف والأداة والإعدادات.
3. يوقّع على نطاق الفحص (scopeSigned).
4. يرسل النظام الطلب → يستلم 202 Accepted.
5. يُوجَّه لصفحة تفاصيل الفحص.

### UC-02: تصدير تقرير PDF

**الفاعل:** مستخدم | **الشرط:** فحص مكتمل

1. يفتح تفاصيل الفحص.
2. يضغط "تصدير PDF".
3. يُحمَّل ملف PDF.

### UC-03: إنشاء تذاكر Jira

**الفاعل:** مستخدم | **الشرط:** Jira مربوط، فحص به ثغرات

1. يضغط "إنشاء تذاكر Jira".
2. يُنشئ النظام تذكرة لكل ثغرة (أو حسب الإعداد).
3. يعرض عدد التذاكر المُنشأة والمتخطاة.

### UC-04: إدارة الطابور (Admin)

**الفاعل:** مدير | **التدفق:** عرض الطابور، إعادة ترتيب، حذف مهمة، إلغاء الكل.

### UC-05: اقتراح إعداد فحص بالذكاء الاصطناعي

**الفاعل:** مستخدم | **التدفق:** Guided Setup → أسئلة → توصية → إنشاء فحص.

## 3.5 قيود النظام

1. لا يدعم النظام حل CAPTCHA تلقائياً؛ يُوصى بجلسات مصدّقة.
2. كود الـ Backend غير مضمّن في مستودع الواجهة؛ التحليل مبني على OpenAPI.
3. تنفيذ الفحص يعتمد على توافر خادم VPS والـ API الخلفي.
4. بعض قيود الباقة تمنع الفحص المصدّق أو أدوات brute-force (ffuf) حسب الإعداد.

## 3.6 قواعد العمل (Business Rules)

- كل فحص يستهلك رصيداً (credit) من باقة المستخدم.
- `max_runtime_minutes` يحدّ وقت التنفيذ على VPS.
- `allow_auth_scanning=false` يرفض طلبات تحتوي token مصادقة.
- `allow_bruteforce=false` يمنع ffuf أو معاملات brute-force.
- الفحص يتطلب `scopeSigned=true` تأكيداً على نطاق قانوني.
